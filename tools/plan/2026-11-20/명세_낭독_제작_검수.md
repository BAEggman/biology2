## 1. 상태 — 한 구간(과 · sid)이 지나는 길
`hold → content_verified → script_locked → audio_generated → audio_ai_ok → published` (+ 사용자가 들으면 「들어 봄」)
| 상태 | 뜻 | 누가 올리나 |
|---|---|---|
| hold | 내용 · 그림에 열린 항목이 있다 | 대장 |
| content_verified | 그 과(또는 그 구간)가 승급 조건(지시서 §5)을 통과 | Opus |
| script_locked | 잠금 목록 `tools/audio/locked.json` 에 `say` 의 sha256 · 그림 blob · 발음 사전 판 · 승급 쪽지를 적음 — **녹음해도 되는 구간의 목록**(어느 도구가 녹음하든 이 목록에 있는 것만) | Opus |
| audio_generated | 파일을 받았고 §4 를 통과 | 녹음한 도구 |
| audio_ai_ok | §5 의 AI 검수 통과(가벼운 흔들림은 적어 두고 수용) | 녹음한 도구 |
| published | 공개 주소에서 실제로 재생됨을 확인 | 올린 뒤 |
- 떨어지면 `audio_rejected`(사유 부호 §9) 또는 `audio_review_pending`(AI 검수가 갈림 — 사람이 들어야 정해짐). 둘 다 **싣지 않는다** — 그 구간은 기기 음성이 읽는다.
- manifest 는 다른 도구의 꼴 그대로: `{src, text, status: "ready", sha256}`. **새 상태값 · 새 칸을 만들지 않는다**(둘이 쓰는 파일이다). `ready` 의 뜻은 「AI 검수까지」이고, 사용자가 들은 구간은 따로 `lesson/audio/heard.json`(`{과: [sid …]}`)에 적는다 — 화면의 「Gemini 녹음 · AI 검수」 / 「Gemini 녹음 · 들어 봄」은 그 파일로 가른다(11-19 명세 §1.9 의 3).
- 글 · 발음 사전 · 그림이 바뀌면 그 구간은 `script_locked` 앞으로 돌아간다. 글이 바뀐 녹음은 재생기가 저절로 건너뛴다(`text !== say`) — 그 항목을 manifest 에서 빼고(파일은 남김) 검수 기록에 `superseded_by_text_change` 로 적은 뒤 다시 만들 목록에 올린다. 낭독 내용과 무관한 그림 손질(빛깔 · 이음매 · 다른 구간의 새 소품)은 까닭을 적고 유지할 수 있다.
- **이미 녹음된 8과**는 Opus 의 승급을 거치지 않았다(그 도구는 「그림–대본 대응을 봤다 · 과학 전수 재감사는 아니다」라고 적었다). 지시서 0단계에서 그 8과를 먼저 승급 검사한다 — 통과하면 잠금 목록에 올리고, 고칠 것이 나오면 고친 구간만 다시 만든다.

## 2. 대본 잠금과 낭독 입력
1. 그 과가 `content_verified` 인지 대장에서 확인한다(구간 단위도 된다 — 열린 항목이 닿지 않고, 다시 그릴 구역에 들지 않은 sid).
2. `node tools/audio/spoken.js <과>`(만들 연장) — sid 마다 `say` · `say_sha256` · `spoken_text`(= `tools/tts_norm.js` 의 `ttsNorm(say)`) · `spoken_sha256` · 그 구간에 쓰인 치환(표기 → 읽는 말) · 자수 · 예상 길이를 낸다(올라온 43 구간은 초당 4.8 ~ 7.9자 · 가운데값 6.0자 — 받아들이는 범위는 초당 4.3 ~ 9자. 그보다 빠르면 빠뜨림, 느리면 덧말을 의심한다).
3. `spoken_text` 에 로마자 · 기호가 남았으면 멈춘다(낭독 문 — 11-19 명세 §2.5). 사전을 고치고 다시.
4. 사전의 씨앗: 그 도구가 이미 쓴 치환이 검수 기록에 남아 있다(G → 지 · 2n → 이 엔 · n → 엔 따위 · `normalization_notes` · `minor_issues`) — 그 읽기를 사전에 먼저 옮겨 **같은 표기를 두 도구가 다르게 읽히지 않게** 한다. ENaC 는 사용자가 정한 「이 엔 에이 씨」.
5. 잠금 목록에 올린다. 다음부터는 낭독 입력 `spoken_text`(또는 그 sha256)와 쓰인 치환을 검수 기록에 함께 남긴다 — 지금까지의 58 구간은 낭독 입력이 저장소에 없다.

## 3. Gemini 에서 만들기(Claude in Chrome)
1. 탭 목록을 먼저 본다. **다른 생성이 돌고 있으면 겹쳐 내지 않는다**(다른 도구가 쓰는 중일 수 있다). 사용자의 음성 작업 대화(주소는 인계문 §8.1 — 공개 저장소에 적지 않는다)를 참고하되, 같은 계정에서 새 작업을 연다.
2. **작업(Task) 모드**가 메뉴에 보이면 그것을 쓴다(지금 통하는 길). 이름과 자리는 화면에서 확인한다 — 옛 자리를 믿지 않는다. 보이는 모델 알약 · 설정 · 목소리 이름을 **보이는 그대로** 적는다(`observed_model` · `observed_effort` · `voice` — 안 보이면 `unknown`).
3. 과 하나를 한 작업으로: 프롬프트는 인계문 §8.4 의 틀 + 그 과의 구간 목록(구간마다 파일 하나 · `biology_<과>_<sid>_v<n>.wav` · ZIP 하나로). `<대본>` 에는 `spoken_text` 만. 목소리는 지금까지와 같은 것(기록에는 Kore)을 청한다 — 고를 수 없으면 그렇게 적고 닮음은 §5 에서 본다.
4. 만든 쪽에게 자기 검수를 시켜도 되지만 **그것만으로 통과시키지 않는다**(§5).
5. 실제 파일이 나와야 만든 것이다 — 글로 「만들었습니다」라고만 하면 실패(`no_audio`). 내려받는다 → `device_list_dir` 로 `~/Downloads` 에 새 파일이 생겼는지(이름 · 크기 · 시각) 확인 → `~/Downloads/b2audio/raw/<과>/` 로 옮긴다(`mv` — 지우지 않는다). 단추를 눌렀다는 것과 파일이 저장됐다는 것을 따로 적는다.
6. 멈추는 때: 로그인 · 약관 · 동의 · CAPTCHA · 결제 · 권한 창 → 사용자에게 알리고 그 일만 맡긴다 / 한도에 걸렸다는 알림 → 그날은 끝(다른 계정 · 모델로 돌아가지 않는다) / 같은 오류가 세 번 → 멈추고 보고.

## 4. 받은 파일 검사(사용자 컴퓨터 쪽 · ffprobe · ffmpeg · python)
- ZIP 이 온전한가 · 구간 수만큼 WAV 가 있는가 · 풀리는가(HTML 오류 쪽에 `.wav` 이름만 붙은 것 아님) · 채널 · 샘플레이트 · 길이.
- 길이가 예상 범위 안인가 — 짧으면 뒤가 잘렸거나 빠뜨림, 길면 덧말.
- 앞뒤 무음 · 클리핑(최댓값이 0 dBFS 에 붙음) · 끝이 말 중간에서 끊김. 배포본에서 앞뒤 무음을 다듬을 때는 그 도구가 한 것처럼 여유를 두고(무음 문턱 −55 dBFS 쯤 · 몇 ms 의 여유와 페이드) 첫소리 · 끝소리를 자르지 않는다. 원본은 그대로 둔다.
- 여러 구간을 한 파일로 받았다면: 무음 구간과 받아쓴 글의 시각(§5)으로 문단 경계를 확인한 뒤 무음 한가운데에서 자른다. 다른 파일의 자른 자리(22.83초)를 옮겨 쓰지 않는다.
- 원본 WAV 는 `~/Downloads/b2audio/raw/` 에 둔다(저장소에 넣지 않는다). sha256 을 기록에 적는다 — 비트레이트를 바꾸게 되면 원본에서 다시 만든다.

## 5. AI 검수 — 세션이 「검수」라고 말할 수 있는 범위
1. **로컬 대조(늘)** — manifest 에 넣을 `text` 가 지금 `say` 와 글자까지 같은가 · 낭독 입력의 치환이 사전에 있는 것뿐인가 · 해시 · 길이 · 풀림.
2. **따로 연 Gemini 가 듣기(늘)** — 만든 대화가 아닌 **새 작업**에 WAV 만 준다.
   - 먼저 **대본을 주지 않고** 「들리는 그대로 받아써라 — 고쳐 쓰지 말고, 흐리게 들린 데는 들린 대로」. 대본을 먼저 보이면 고쳐 듣는다.
   - 받아쓴 글을 세션이 `spoken_text` 와 맞춰 본다(띄어쓰기 · 문장부호를 지우고 · 지/쥐, 베/배, 중계/중개 같은 모음 합류는 같게 침 — 그 도구가 쓴 다듬기). 어긋난 자리를 낱낱이 뽑는다.
   - 어긋난 자리마다 그 대목만 다시 들려(보통 속도와 느린 속도) 「무엇으로 들리는가」를 묻는다.
   - 그다음 대본을 주고 **꼭 들려야 하는 것**을 하나씩 확인시킨다: 숫자 · 단위 전부 / 부정 표현(않 · 없 · 아니 · 못 · 말)의 수와 자리 / 방향 · 차례(에서 … 로 · 먼저 · 다음 · 왼 · 오른 · 위 · 아래 · 오 프라임 · 삼 프라임) / 혼동쌍(관강 · 관광, 분비 · 재흡수, 유입 · 방출, 활성 · 억제, 전 · 후, 상승 · 감소, 불완전 · 완전) / 사전 항목과 그 구간의 고리 낱말(라이터 · 낫 …) / 맨 앞 · 맨 끝 열두 자(인사 · 제목을 읽지 않았는가 · 뒤가 빠지지 않았는가) / 존댓말로 바뀌지 않았는가 · 목소리가 앞 구간과 같은가.
   - 받아쓴 글이 대본과 **쉼표 하나까지 똑같으면** 의심한다(대본을 본 것이 아닌지) — 그 작업을 버리고 새로 연다.
3. **선택 — 음성 인식 모델을 겹쳐 보기**(사용자 컴퓨터 쪽 작업 공간 · `pip install sherpa-onnx` 와 GitHub 릴리스의 한국어 인식 모델 — **내려받기이므로 허락을 먼저 받는다**: 파일 이름 · 출처 · 크기). 쓰는 때: Gemini 의 듣기가 갈리는 구간 · 묶음마다 표본 열에 하나. 허락이 없으면 건너뛴다 — 그 구간은 `audio_review_pending`.
4. **판정**(사용자의 수용 기준)
   | 판정 | 조건 | 다음 |
   |---|---|---|
   | 통과 | 어긋난 자리 없음 · 꼭 들려야 하는 것 모두 맞음 | §7 로 |
   | 가벼운 흔들림 수용 | 뜻이 통하는 조음의 흐림만 남음(낱말이 다른 낱말로 들리지는 않음) | 무엇이 어떻게 들리는지 `retained_minor_issues` 에 적고 §7 로 |
   | 다시 | 누락 · 덧말 · 인사/제목 · 존댓말 · 수/부정/방향이 다름 · 혼동쌍이 바뀌어 들림 · 용어가 다른 낱말로 들림 · 목소리가 바뀜 | §9 |
   | 갈림 | 듣기가 물을 때마다 다름 | 다시 한 번 만들고, 그래도 갈리면 `audio_review_pending` → 사람 청취 목록 |
- 기록에는 듣기를 **누가** 했는지 적는다: `review_independent: true`(따로 연 작업) / `false`(만든 쪽의 자기 검수뿐). Opus 가 올리는 것은 모두 true 여야 한다.
- AI 가 들었다고 사람이 들은 것은 아니다. 그래서 통과분도 「AI 검수」로만 적는다(`human_listening: false`).

## 6. 사람 청취 — 사용자가 하는 몫을 가장 작게
- **먼저 한 번**: 이미 올라온 58 구간 가운데 열다섯쯤을 사용자가 들어 본다(8분쯤 — L23c s2 · 자기 검수만 거친 L14a · L05b · L36d · L49b · L36b 에서 고루 · 과 화면에서 그대로 들으면 된다). 묻는 것 셋: 목소리와 속도가 괜찮은가 · 수용 기준(가벼운 흔들림)이 귀에 맞는가 · 틀리게 읽은 데가 있는가. 답으로 §5 의 판정을 고쳐 잡는다.
- 그 뒤로는 공부하며 듣는 것이 곧 청취다 — 끝까지 들은 구간은 재생기가 적어 두고(`lesson_heard`), 이상하면 🚩(`lesson_flags`). 과 목록의 「내보내기」로 복사해 주면 `lesson/audio/heard.json` 과 다시 만들 목록에 반영한다.
- 사용자가 🚩 한 종류의 잘못(예: 어떤 약어를 늘 틀리게 읽음)은 같은 낱말이 든 구간을 모두 다시 검수한다 — 한 구간만 고치고 끝내지 않는다.

## 7. 배포본 만들기와 싣기
1. 원본 WAV → MP3 mono 24 kHz. 비트레이트는 지금 값(96 kbps)을 따르되 §11 의 결정에 따라 바꾼다 — 바꿀 때는 **원본 WAV 에서 다시 만든다**(MP3 를 다시 누르지 않는다). 파일명 `lesson/audio/<과>_<sid>_v<n>.mp3` — 다시 만들면 n 을 올린다(캐시).
2. 배포본도 한 번 더 풀림 · 길이를 본다.
3. 사용자 컴퓨터 → 컨테이너(`device_stage_files`) → `lesson/audio/` → manifest 항목 `{src, text(= say 그대로), status: "ready", sha256}`.
4. **manifest 는 둘이 쓰는 파일이다.** 고치기 직전에 fetch — 달라졌으면 옮겨 실은 뒤 고친다. 다른 도구의 항목을 지우거나 덮지 않는다(같은 구간을 새 판으로 바꿀 때 · 글이 바뀌어 무효가 된 항목을 뺄 때만 그 줄을 고친다). 파일 전체를 다시 쓰지 말고 항목을 더한다.
5. 검수 기록 `lesson/audio/reviews/<날짜>-batch-<nn>.json`(§8) · `node tools/build_lesson.js <과>` · `node test/all.js`(새 `test/verify_audio.js`: 항목마다 파일 있음 · sha256 같음 · `text` 가 지금 `say` 와 같음(다르면 그 항목을 낱낱이 알림) · 검수 기록에 그 파일이 있음 · 주소가 `blob:`/로컬/Gemini 주소가 아님).
6. 컨테이너에서 실제 재생 확인(Playwright · 로컬 서버 · 자동 재생 허용): 그 구간에서 상태 글이 「Gemini 녹음…」 · 끝나면 다음 구간으로 · 다음/이전/멈춤을 빠르게 눌러도 겹치지 않음 · 글을 한 글자 바꾸면 기기 음성으로 내려감.
7. 커밋은 **음성만 따로**(글 · 그림 · 재생기 커밋과 섞지 않는다) → fetch → 번들 → 사용자가 올림 → 공개 주소에서 다시 확인(파일이 200 · 재생 시간 · 끝 사건) → `published`.

## 8. 검수 기록의 칸 — 다른 도구의 꼴에 맞춘다
묶음마다 `lesson/audio/reviews/<날짜>-batch-<nn>.json`. 새 대장 꼴을 만들지 않는다. 구간마다:
`lesson_id · sid · version · source_commit · say_sha256 · wav_sha256 · mp3_sha256 · bytes · duration_s · source_text_match · content_check · audio_review(방법) · human_listening(false) · pronunciation_status(PASS · ACCEPT_WITH_MINOR_PRONUNCIATION_VARIATION · HOLD) · retained_minor_issues`
— 여기에 우리가 더하는 칸: `spoken_sha256` · 쓰인 치환 · `image_blob` · `locked`(잠금 목록의 줄) · `review_independent` · `attempts`(시도마다 무엇이 어디서 어떻게 들렸는지) · `observed_model` · `observed_effort` · `voice` · `reason`(떨어진 사유 부호).
- 떨어진 시도도 남긴다. 만든 횟수와 살아남은 구간 수를 따로 센다.
- 다른 도구가 쓴 기록 파일은 고쳐 쓰지 않는다. 그 구간이 무효가 되면 새 묶음 파일에 `superseded…` 로 적는다.
- `tools/audio-narration.md`(그 도구의 짧은 안내)는 그대로 두고, `tools/audio/README.md` 에 이 명세를 가리키는 한 쪽을 둔다(문턱 · 까닭 · 사전의 판).

## 9. 다시 만들기와 실패 사유
- 다시 만들 때는 인계문 §8.4 의 재생성 틀: 어디서 무엇이 어떻게 들렸는지 · 목소리와 속도는 그대로 · 같은 대본 전체를 다시 · 새 판 번호. **낱말을 빼서 읽기 쉽게 만들지 않는다.** 용어 때문에 되풀이해 틀리면 사전의 읽기를 고치고(판 번호를 올림) 그 낱말이 든 다른 구간도 본다.
- 한 구간에 세 번까지(그 도구는 L36b s2 를 네 번째에 통과시켰다 — 넷째는 사용자가 허락한 과에서만). 끝내 안 되면 `audio_rejected` 로 두고 보고에 올린다 — 기기 음성이 그 구간을 읽는다(내용은 통과한 구간이므로).
- 사유 부호: `no_audio`(파일이 안 나옴) · `decode`(안 풀림) · `truncated`(뒤 빠짐) · `added`(덧말 · 인사 · 제목) · `polite`(존댓말로 바뀜) · `number` · `negation` · `direction` · `term`(용어가 다른 낱말로) · `confusable`(혼동쌍) · `voice`(목소리 바뀜) · `pace`(속도) · `noise`(잡음 · 클리핑) · `split`(자른 자리) · `limit`(한도) · `ui`(앱 화면이 바뀌어 못 함) · `busy`(다른 도구가 쓰는 중).

## 11. 어디에 두나 — 지금 정해야 한다
- 지금 값(96 kbps · 본 저장소의 `lesson/audio/`)으로는 덱의 4분의 3쯤에서 Pages 한도 1 GB 를 넘는다(§0). 저장소 이력도 권장선에 닿아 있다.
- 길 셋(사용자 결정 — 지시서 §11 의 3):
  | 길 | 얻는 것 | 드는 것 |
  |---|---|---|
  | 가. 음성만 담는 저장소(`biology2-audio` + Pages) | 음성에 1 GB 가 따로 생긴다 · 본 저장소 이력이 더 안 붇는다 · manifest 의 `src` 를 온전한 https 주소로 적으면 재생기는 그대로 돈다(같은 `baeggman.github.io`) | 사용자가 저장소를 하나 만들고 Pages 를 켠다 · 이미 올린 56 파일을 옮긴다 · 올리는 스크립트에 저장소가 하나 더 |
  | 나. 비트레이트를 낮춘다(64 kbps → 전 덱 약 445 MB) | 본 저장소 그대로 간다(합 약 930 MB — 빠듯함) | 원본 WAV 에서 56 파일을 다시 만든다 · 자음과 숫자가 뭉개지지 않는지 듣기 검수를 다시 |
  | 다. 작업 폴더를 Pages 밖으로(`tools/blind` · `tools/prompts` 308 MB 를 내보내지 않게) | 본 저장소에 자리가 난다 | Pages 를 Actions 배포로 바꾸거나 폴더를 다른 곳으로 옮긴다 — 손이 많이 간다 |
  기본값: **가**(가장 깨끗하다). 정해질 때까지는 지금 자리에 싣되, `lesson/audio/` 가 150 MB 에 이르면 멈추고 묻는다.
- Git LFS 포인터 · Releases · `blob:` · Gemini 대화 주소 · 만료되는 내려받기 주소는 음원 주소로 쓰지 않는다. 음성을 HTML 에 Base64 로 넣지 않는다.

## 12. 하지 않는 것
- 듣지 않고 「청취 완료」라 적지 않는다. 만든 쪽 Gemini 가 「품질 확인 완료」라 했다고 통과시키지 않는다.
- 잠금 목록에 없는 구간 · 보류 · 초안 대본을 만들기 줄에 넣지 않는다. 142과를 한꺼번에 만들지 않는다.
- 다른 도구가 Gemini 를 쓰는 동안 겹쳐 내지 않는다. 그 도구의 manifest 항목 · 검수 기록을 고쳐 쓰지 않는다.
- 공개 페이지가 Gemini 앱을 그때그때 불러 음성을 만들게 하지 않는다 — 한 번 만들어 검수하고 저장한 파일을 되풀이해 쓴다.
- 사용자의 스피커로 소리를 내지 않는다(공개 확인은 음소거 재생 · 시간 진행으로).
